# Direct Ecto escape hatches

Ash owns normal CRUD and user-facing domain actions. Each direct `Repo` call
below needs PostgreSQL-specific behavior, a hot ingest path, or bounded
maintenance. Each query repeats its tenant predicate where tenant data is
addressed directly.

| Area | Modules | Reason |
| --- | --- | --- |
| Billing | `entitlements`, `plan_resolver`, `usage_rollover`, `webhook_processor` | Capacity locks, Stripe idempotency claims, subscription ordering, and usage rollover require transactional SQL or row locks. |
| Orgs | `apply_billing_plan/3` | The Stripe-derived Organization plan transition shares Billing's webhook transaction with subscription ordering and webhook completion. |
| Measure | `dashboard`, `public_evidence`, `ingest`, `quota`, `rollups`, `retention`, `maintenance_worker` | The dashboard and the public homepage evidence need bounded grouped ranking and equal-period aggregate queries; Ash reads cannot express `GROUP BY value ORDER BY SUM(...)` without loading every dimension row. Both repeat the org, project, source, and environment predicate in the query. The high-volume ingest path, atomic counters, capped dimensions, and bulk pruning must avoid per-hit Ash actions. |
| Monitor | `active_check_outcome`, `heartbeat`, `scheduler`, `monitor_creator`, `record_pause_interval`, `rollup`, `retention`, `expiry_scan`, `maintenance_worker`, `entitlements`, `monitor_metrics`, `public_evidence` | Scheduler outcome commits need row locks and one transaction; runtime scheduling, rollups, expiry scans, plan counts, and retention are OTP or maintenance work. `monitor_metrics` uses bounded PostgreSQL ordered-set aggregates, grouped percentile buckets, histogram counts, and response composition because Ash cannot express these without loading check history. `public_evidence` buckets the public marketing homepage hero by `date_trunc('hour' or 'day', checked_at)` and counts the last 24 hours per monitor; Ash reads cannot express `GROUP BY date_trunc(...)` or a filtered count without loading thousands of check rows. Both queries repeat the org, project, monitor and `environment = 'production'` predicate, and select counts and an average latency only. |
| Observe | `event_writer`, `payload_storage_worker`, `alert_worker`, `session_rollup_writer`, `alert_router`, `quota`, `retention`, `maintenance_worker`, `release_health`, `dashboard`, `source_id_backfill.runner`, `public_evidence` | Partitioned event writes, global client-id/session-id deduplication, cooldown claims, quota counters, partition pruning, and release/trend counts read a raw partitioned table (`error_events`) that has no Ash resource; overflow storage and post-commit alert jobs use persisted event/outbox IDs; the one-time `source_id` backfill (issue #46 follow-up) batches raw updates across `issues`, `releases`, `error_events`, and `observe_session_rollups` by primary key. `public_evidence` counts issues per hour or per day with `GROUP BY date_trunc(...)` for the public marketing homepage; a capped Ash read would report a false count, and the query returns current durable state. |
| Analytics | `ingest`, `queries`, `retention_policy`, `maintenance_worker` | `product_events` has no Ash resource (ADR 0007). Ingest writes up to 100 rows per request in one statement and deduplicates on a client id, which no per-event Ash action can express affordably. Every read is a grouped aggregate: `count(DISTINCT distinct_id)`, `date_trunc` buckets, `GROUP BY properties ->> key`, and the chained self-joins a funnel needs; an Ash read would load every matching event row into the VM instead. Retention deletes historical rows in bounded batches. Every statement repeats the org and project predicate, and every property name and value is a bound parameter, never interpolated. |
| Notifications | `delivery_worker`, `monitor_router` | The delivery ledger needs lease/fencing and idempotent external-effect claims. |
| Status | `queries`, `service_overview`, `public_page`, `maintenance_worker`, `recovery_worker` | `queries`, `service_overview`, and `public_page` use bounded project-scoped aggregate and cross-resource projections for private and public health views. Ash owns component-monitor and maintenance-monitor reads, creation, and deletion. `maintenance_worker` locks maintenance and monitor rows, then records pause ownership in one transaction. `recovery_worker` locks the global set of resolved Monitor incidents that still need a Status recovery update, so concurrent jobs publish one update per incident. |
| Health | `AlplusWeb.HealthController` | The load balancer must verify the same database dependency as application requests. |
| Growth | `Alplus.Growth.Funnel`, `Alplus.Growth.HealthCheck`, `Alplus.Growth.Retention` | Cross-tenant acquisition and founder observability reporting. It aggregates over every organization at once and so belongs to no tenant: there is no actor whose policies could scope it, and every Ash read path involved is project-scoped and would return nothing. Read-only aggregates over indexed foreign keys, taking no user input beyond a time window. Retention rolls 30-day journey events into daily counts, then deletes the events. The observability aggregate is reachable only through the founder-gated `/admin` route. |

No listed path accepts an interactive browser actor as its authorization
mechanism. Hot paths authenticate at their controller boundary. Maintenance
and scheduler paths use explicit org/project predicates or durable worker
arguments. New direct `Repo` calls must be added to this file and justified
at the call site.
